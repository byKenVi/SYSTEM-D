1. RÈGLE MÉTIER DES PRODUITS SYSTÈME D
==================================================

Règle métier confirmée :

Un produit Système D est un produit Zoho Inventory qui n’est assigné à aucun client.

Dans Zoho, cette absence d’assignation est représentée par le champ cf_client :
- si cf_client est vide, null, absent parce qu’il n’a aucune valeur, ou équivalent selon la structure réelle de Zoho, alors le produit est un produit Système D ;
- si cf_client contient une valeur client, alors le produit appartient à ce client uniquement ;
- un produit avec cf_client rempli ne doit jamais apparaître dans la Boutique Système D ;
- un produit assigné à un client ne doit jamais être visible par les autres clients.

ATTENTION :
Ne confonds pas deux situations différentes :

1. Le produit a été correctement récupéré depuis Zoho, les custom_fields sont lisibles, et cf_client est réellement vide ou non renseigné.
   => Ce produit est un produit Système D.

2. Le produit n’a pas pu être complètement récupéré depuis Zoho, ou les custom_fields/cf_client sont absents à cause d’une erreur API, d’un fallback, d’un quota atteint, d’une réponse partielle ou d’un problème de parsing.
   => Ce produit ne doit PAS être automatiquement traité comme Système D.
   => Il doit être marqué comme unresolved jusqu’à ce qu’une synchronisation complète confirme son statut.

Donc la logique correcte n’est pas simplement :

contact_id IS NULL = produit Système D

La logique correcte est :

- cf_client confirmé vide / non renseigné dans une réponse Zoho complète et fiable = produit Système D ;
- cf_client rempli et résolu = produit client ;
- cf_client rempli mais non résolu = produit unresolved, caché des portails clients ;
- custom_fields ou cf_client impossibles à vérifier à cause d’une réponse incomplète = produit unresolved, caché des portails clients.

Les produits unresolved doivent être visibles côté administration avec un avertissement, mais jamais exposés aux clients.

Objectif :
Respecter la règle métier “pas de cf_client = produit Système D”, tout en évitant qu’une erreur de récupération Zoho transforme par erreur un produit client en produit public.

3. SYNCHRONISATION COMPLÈTE SÛRE
==================================================

La synchronisation ne doit jamais supprimer ou masquer des produits parce qu’une page Zoho a échoué.

Propose un mécanisme de sync run comprenant au minimum :

- un identifiant de cycle de synchronisation ;
- un statut running, success ou failed ;
- le nombre de pages attendues et reçues ;
- le nombre de produits reçus ;
- started_at ;
- completed_at ;
- error_message.

Algorithme attendu :

1. Obtenir un verrou atomique.
2. Créer un sync run.
3. Récupérer toutes les pages Zoho.
4. Vérifier qu’aucune page n’a échoué.
5. Valider et normaliser toutes les données.
6. Démarrer une transaction DB.
7. Upsert les produits par zoho_item_id.
8. Marquer les produits vus avec le sync_run_id.
9. Uniquement si la récupération complète a réussi, marquer comme supprimés les produits non vus.
10. Valider la transaction.
11. Marquer le sync run comme success.
12. Libérer le verrou dans un bloc finally.

En cas d’échec avant la fin :
- ne marque aucun produit comme supprimé ;
- conserve le catalogue précédent ;
- marque le cycle comme failed ;
- journalise la cause.

Utilise une suppression logique :
- is_deleted ou deleted_at ;
- pas de suppression physique immédiate.

Explique comment les anciennes commandes conserveront leurs références produit.
